# Практическая работа: нормализация БД до 3НФ

## Тема

**Нормализация реляционной базы данных до третьей нормальной формы (3НФ).**

Пример предметной области — онлайн-каталог фильмов по типу Кинопоиска.

## Цель

Научиться:
- определять функциональные зависимости;
- приводить таблицы к 1НФ, 2НФ и 3НФ;
- находить частичные и транзитивные функциональные зависимости;
- отличать транзитивную зависимость от рекурсивной связи;
- строить итоговую ER-диаграмму.

# Что такое нормальные формы

Нормализация — это последовательное приведение структуры реляционной базы данных к форме, в которой данные хранятся без лишнего дублирования и зависимости одних неключевых данных от других.

В этой работе необходимо проверить модель на соответствие **1НФ, 2НФ и 3НФ**. Важно не запоминать только названия форм, а каждый раз задавать себе вопрос: **какую зависимость или проблему я сейчас ищу?**

## 1НФ — атомарность значений

Для 1НФ необходимо проверить, что каждое поле содержит **одно значение**, а не список значений или повторяющуюся группу.

При проверке таблицы ищите:
- несколько значений в одной ячейке;
- списки, записанные через запятую;
- несколько сущностей, объединённых в одном поле;
- повторяющиеся группы столбцов.

Например:

~~~text
Genres = "Фантастика, Драма"
Actors = "Актёр 1, Актёр 2"
~~~

При анализе задайте вопрос:

> Можно ли рассматривать значение каждой ячейки как одно отдельное значение?

Если нет — необходимо определить, как представить эти данные в реляционной модели.

**1НФ отвечает прежде всего на вопрос об атомарности данных.**

## 2НФ — зависимость от всего составного ключа

2НФ имеет значение, когда таблица содержит **составной первичный ключ**, то есть ключ состоит из нескольких полей.

Для каждого неключевого атрибута нужно проверить:

> Он зависит от всего составного ключа или только от его части?

Например, если ключ состоит из:

~~~text
(A, B)
~~~

необходимо проверить зависимости вида:

~~~text
A → C
B → C
(A, B) → C
~~~

Если неключевой атрибут определяется только одной частью составного ключа, это **частичная функциональная зависимость**.

При проверке 2НФ ищите именно такие зависимости.

**2НФ отвечает на вопрос: зависит ли каждый неключевой атрибут от всего составного ключа?**

## 3НФ — отсутствие транзитивных зависимостей

После проверки 2НФ необходимо проверить зависимости между неключевыми атрибутами.

Ищите цепочки вида:

~~~text
A → B
B → C
~~~

Если `A` является ключом, а `B` и `C` — неключевыми атрибутами, то через `B` возникает **транзитивная функциональная зависимость**:

~~~text
A → B → C
~~~

При проверке 3НФ задайте вопрос:

> Может ли один неключевой атрибут определить другой неключевой атрибут?

Если да, такую зависимость необходимо исследовать и определить, не требуется ли разделение сущностей.

**3НФ отвечает на вопрос: нет ли зависимости неключевого атрибута от другого неключевого атрибута через цепочку зависимостей?**

## Не путайте транзитивную зависимость и рекурсивную связь

Это разные понятия.

**Транзитивная функциональная зависимость** описывает зависимость атрибутов:

~~~text
A → B
B → C
A → C
~~~

При приведении к 3НФ такие зависимости анализируются и, если они нарушают требования 3НФ, устраняются изменением структуры данных.

**Рекурсивная связь** описывает связь записи с другой записью **той же таблицы**.

Например:

~~~text
genres.parent_genre_id → genres.id
~~~

Так можно представить иерархию:

~~~text
Жанр
└── Фантастика
    └── Научная фантастика
        └── Космическая фантастика
~~~

Рекурсивная связь сама по себе **не является нарушением нормализации**. Если предметная область содержит иерархию, такая связь может и должна присутствовать в нормализованной базе данных.

При работе с рекурсивной связью нужно проверить не её наличие как таковое, а то, что остальные атрибуты таблицы имеют корректные функциональные зависимости.

## Краткая схема проверки

~~~text
1НФ → атомарны ли значения?
        ↓
2НФ → зависят ли неключевые атрибуты от всего составного ключа?
        ↓
3НФ → нет ли транзитивных зависимостей между неключевыми атрибутами?
~~~

Эти правила дают критерии проверки. **Конкретную структуру итоговых таблиц необходимо определить самостоятельно на основании исходных данных и найденных зависимостей.**

# 6. Транзитивная и рекурсивная зависимости — это не одно и то же

Обязательно письменно объясните разницу.

### Транзитивная зависимость

Это цепочка функциональных зависимостей между атрибутами:

~~~
A → B
B → C
~~~

В результате:

~~~
A → C
~~~

Именно такие зависимости устраняются при приведении таблицы к 3НФ.

### Рекурсивная связь

Рекурсивная связь возникает, когда запись таблицы ссылается на другую запись **той же таблицы**.

Например, в таблице `genres`:

| id | name | parent_genre_id |
|---:|---|---:|
| 1 | Кино | NULL |
| 2 | Фантастика | 1 |
| 3 | Научная фантастика | 2 |

Здесь `parent_genre_id` является внешним ключом на `genres.id`.

Это **не то же самое**, что транзитивная функциональная зависимость.

Рекурсивная связь сама по себе **не является нарушением нормализации**.

Она может и должна существовать в корректной нормализованной БД, если предметная область содержит иерархию:

~~~
Жанр
└── Фантастика
    └── Научная фантастика
        └── Космическая фантастика
~~~

### Требуется

Добавьте в итоговую ER-модель иерархию жанров через рекурсивный внешний ключ:

~~~
genres.parent_genre_id → genres.id
~~~

Объясните, почему наличие этого внешнего ключа не означает нарушение 3НФ.
